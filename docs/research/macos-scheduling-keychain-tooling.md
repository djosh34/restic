# Research: scheduling, Keychain and tooling around restic on macOS

Ticket: #5 (part of map #1). Research cutoff: 2026-10-10.
Baseline: **restic 0.19.1** (latest, released 2026-07-05, tag `6aa3a51`). Unless a claim names another version, it was checked against the `v0.19.1` tag. Source links are pinned to tags or commits.

## TL;DR

- **Restic still has no scheduler, by design.** Its docs point users to OS schedulers or resticprofile ([doc/040_backup.rst L760-771](https://github.com/restic/restic/blob/v0.19.1/doc/040_backup.rst#L760-L771)). On a Mac laptop, **cron is the wrong tool**: jobs missed during sleep never run, and cron needs Full Disk Access. **launchd `StartCalendarInterval`** runs a missed job once on wake. `StartInterval` does not ([launchd.plist(5)](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/launchd.plist.5.html#L445-L467), [Apple: Scheduling Timed Jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)). The user's "cron by hand" pain is real, but most of it comes from picking cron.
- **Keychain: restic has no native integration, but the documented hooks work.** `--password-command '/usr/bin/security find-generic-password … -w'` is in restic's own FAQ. S3 keys can come from `credential_process` (since 0.15.0) or from env vars set by a supervisor. Pitfalls: the command runs **without a shell** and **without a timeout**. A LaunchAgent must run in the GUI (Aqua) session to reach the login keychain. A LaunchDaemon must use the System keychain.
- **Wrappers.** resticprofile 0.33.1 (Go) is the best launchd fit. Backrest 1.14.1 (Go) is the best GUI and the closest prior art to the planned supervisor. Neither stores secrets in the Keychain, and both have open lock and status bugs. autorestic, runrestic and crestic leave launchd, wake and Keychain handling to you. The user's "wrappers caused more problems" is **partly confirmed** by open issues and **partly configuration**, e.g. Keychain exit 36 under the wrong launchd session type.
- **Sleep/wake.** Two old failure modes are **fixed**: aborting with "failed to refresh lock in time" after standby (fixed in 0.16.0, #4274) and hung HTTP requests (watchdog added in 0.17.0, 5 min default since 0.17.1). Two limits are **still open by design**: before the first snapshot exists, every retry rescans the whole source, and restic does nothing to stop the Mac from sleeping. Forced sleep, e.g. closing the lid, cannot be prevented, only survived.
- **Files changing during a backup.** Restic 0.19.1 **does not detect or warn** when a file changes while it is being read. That warning existed only in the old archiver, 0.8.x and earlier. **Native APFS snapshots: still open** ([#3714](https://github.com/restic/restic/issues/3714)), and `--use-fs-snapshot` is Windows-only. An external `tmutil` + `mount_apfs` step works. It needs root plus Full Disk Access, and the `device-id-for-hardlinks` feature flag, otherwise every directory looks changed on each run.
- **Full Disk Access** goes to the *responsible process*, not the restic leaf binary. A dedicated, signed native Go executable started directly by launchd is the right entry point. Homebrew upgrades that change paths, and unsigned or ad-hoc-signed binaries, cause the grant to be lost.
- **Alternatives.** Kopia has periodic partial-snapshot checkpoints (45 min) that restic lacks. Duplicacy's CLI does APFS snapshots via `tmutil` (prior art for a Go supervisor). Arq is the most Mac-integrated tool: wake, prevent sleep, APFS by default and Keychain. rustic and Duplicacy are lock-free. Borg 1 has no S3, and Borg 2 is beta and "not for production".

## 2. Scheduling on macOS

- **`StartCalendarInterval`**: a firing missed while asleep runs **on next wake**, and several missed firings coalesce into one. It does **not** wake the Mac. **`StartInterval`**: firings missed while asleep are **dropped**. The old launchd-842 man page claimed otherwise, so don't rely on it. A calendar job missed while **powered off** is not caught up; `RunAtLoad` is a separate start-at-load trigger. Sources: [modern launchd.plist(5) timers](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/launchd.plist.5.html#L445-L467), [old launchd-842 text](https://github.com/apple-oss-distributions/launchd/blob/launchd-842.92.1/man/launchd.plist.5#L251-L262), [Apple guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html).
- **`KeepAlive=true`** means "always restart". It is wrong for a finite backup. `KeepAlive.NetworkState` is documented as **no longer implemented** ([launchd.plist(5) L262-299](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/launchd.plist.5.html#L262-L299)). For a long-running supervisor that decides for itself when to run restic, `KeepAlive` is appropriate *for the supervisor*, not for restic.
- **LaunchAgent vs LaunchDaemon.** `~/Library/LaunchAgents` and `/Library/LaunchAgents` hold *per-user* agents; `/Library/LaunchDaemons` holds system daemons ([launchd.plist(5) FILES](https://keith.github.io/xcode-man-pages/launchd.plist.5.html#FILES), [TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html)). An agent in the `user/<uid>` (Background) domain is a different session from `gui/<uid>` (Aqua). That difference decides whether the login keychain is reachable ([resticprofile #528](https://github.com/creativeprojects/resticprofile/issues/528): `security` exit 36 under `user`, works under `user_logged_on`/Aqua; mapping in [session_type.go](https://github.com/creativeprojects/resticprofile/blob/v0.33.1/darwin/session_type.go#L9-L30)).
- **Overlap.** Restic's docs ask schedulers to detect a run that is already in progress ([040_backup.rst L770-771](https://github.com/restic/restic/blob/v0.19.1/doc/040_backup.rst#L770-L771)). Restic's exit codes let a supervisor classify outcomes: 0 ok, 1 fatal (no snapshot), 3 incomplete snapshot, 10 no repo, 11 locked, 12 wrong password, 130 cancelled by SIGINT/SIGTERM (130 since 0.19.0, #5258) ([cmd_backup.go L48-53](https://github.com/restic/restic/blob/v0.19.1/cmd/restic/cmd_backup.go#L48-L53), [075_scripting.rst L146-170](https://github.com/restic/restic/blob/v0.19.1/doc/075_scripting.rst#L146-L170)). On SIGINT/SIGTERM restic cancels its context and cleans up ([cleanup.go L14-29](https://github.com/restic/restic/blob/v0.19.1/cmd/restic/cleanup.go#L14-L29)), so a supervisor should stop restic with SIGTERM, not SIGKILL.

Common patterns across wrappers:

- **Locks.** Wrappers tend to "fix" restic locks by running `unlock` automatically: Backrest's Auto Unlock ([repo.go L356-369](https://github.com/garethgeorge/backrest/blob/v1.14.1/internal/orchestrator/repo/repo.go#L356-L369)), resticprofile's `force-inactive-lock`, and erikw's script before every run. With one writer that is harmless. With a second reader machine it is not something to automate blindly. Plain `unlock` removes only stale locks; `--remove-all` is dangerous ([lock.go L80-87](https://github.com/restic/restic/blob/v0.19.1/internal/repository/lock.go#L80-L87)).
- **No wrapper makes a weeks-long first backup resumable at a level the user can see.** They all just rerun `restic backup`, and until the first snapshot exists each rerun rescans everything ([faq.rst L6-30](https://github.com/restic/restic/blob/v0.19.1/doc/faq.rst#L6-L30)).
- **Monitoring the last *successful* snapshot is essential.** Hooks don't fire for failures that happen before the hook stage (resticprofile [#237](https://github.com/creativeprojects/resticprofile/issues/237), [#619](https://github.com/creativeprojects/resticprofile/issues/619)), and autorestic marks failed runs as done.
- User sentiment: Backrest replacing brittle scripts on macOS ([HN 2024](https://news.ycombinator.com/item?id=41829913)); scheduled backups failing after sleep on OS X with versions unspecified ([forum #7421](https://forum.restic.net/t/scheduled-backup-failures-after-sleep-on-os-x/7421)).

## 4. Keychain and credentials

### 4.1 Repository password

- **Implementation (0.19.1)**: `--password-command` / `RESTIC_PASSWORD_COMMAND` is split with shell-like rules and run with `exec.Command`. There is **no `/bin/sh -c`**, so pipes and `$HOME` don't work. Stdout is trimmed, and stderr is passed through. There is **no timeout or context**, so a Keychain prompt or a locked keychain can hang restic at startup ([global.go L186-201](https://github.com/restic/restic/blob/v0.19.1/internal/global/global.go#L186-L201)). A password file and a password command are mutually exclusive.
- **Documented macOS recipe** in restic's FAQ: `RESTIC_PASSWORD_COMMAND='security find-generic-password -a … -s … -w'` ([faq.rst L131-149](https://github.com/restic/restic/blob/v0.19.1/doc/faq.rst#L131-L149)). Also seen in real use with an explicit `login.keychain-db` path ([forum #8953](https://forum.restic.net/t/fatal-unable-to-open-repository-input-output-error/8953)).
- **Which keychain** ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)):
  - A daemon outside any user context **must** use a file-based keychain, in practice `/Library/Keychains/System.keychain`.
  - The data-protection keychain exists only in a user login context.
  - The login keychain can be locked, on sleep or after a timeout, independently of item ACLs ([security(1) L323-358](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/security.1.html#L323-L358)).
- **ACL caveat.** With `security`, the Keychain client is `/usr/bin/security`, not restic. Choosing "Always Allow" or `-T /usr/bin/security` therefore trusts *any* caller of that CLI ([security(1) L451-511](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/security.1.html#L451-L511)). A signed helper that calls the Security framework directly gets its own ACL identity.

### 4.2 S3 credentials

- **Credential chain (0.19.1, minio-go v7.1.0)**, in order: static (test only), `AWS_*` env, `MINIO_*` env, AWS shared-credentials file, MinIO client file, IAM/ECS ([s3.go L108-130](https://github.com/restic/restic/blob/v0.19.1/internal/backend/s3/s3.go#L108-L130)). Optional STS assume-role via `RESTIC_AWS_ASSUME_ROLE_*` ([s3.go L152-189](https://github.com/restic/restic/blob/v0.19.1/internal/backend/s3/s3.go#L152-L189)).
- **`credential_process`**: supported since **0.15.0** ([CHANGELOG #3029](https://github.com/restic/restic/blob/v0.19.1/CHANGELOG.md#L3440-L3447)). Caveats from the minio-go implementation:
  - It is read only from the **shared credentials file** (`AWS_SHARED_CREDENTIALS_FILE` or `~/.aws/credentials`, section named by `AWS_PROFILE`), **not** `~/.aws/config`.
  - The command is split with `strings.Fields`, so no quoting is possible, and it needs at least one argument.
  - The returned `Expiration` is honoured, so the provider refreshes.
  
  Source: [file_aws_credentials.go L106-134](https://github.com/minio/minio-go/blob/v7.1.0/pkg/credentials/file_aws_credentials.go#L106-L134). This means a tiny Keychain-reading helper can supply S3 keys with no plaintext on disk.
- **Env credentials** are read once and never refreshed. Temporary STS keys passed in env will expire during a weeks-long run, and env vars take precedence over a refreshing provider ([env_aws.go](https://github.com/minio/minio-go/blob/v7.1.0/pkg/credentials/env_aws.go#L40-L80), [credentials.go L183-219](https://github.com/minio/minio-go/blob/v7.1.0/pkg/credentials/credentials.go#L183-L219)). Static IAM-user keys in env are fine.
- **aws-vault**: the maintained fork is **ByteNess 7.16.2**; the 99designs original (7.2.0) is abandoned. It stores secrets in the Keychain and can act as a `credential_process` or an ECS-style credential server ([README](https://github.com/ByteNess/aws-vault/blob/v7.16.2/README.md#L12-L44), [credential-process.md](https://github.com/ByteNess/aws-vault/blob/v7.16.2/docs/content/docs/credential-process.md#L9-L34)). Interactive MFA, SSO or Touch ID is incompatible with unattended launchd runs.

## 5. Full Disk Access, sleep and wake

### 5.1 Full Disk Access (TCC)

- Full Disk Access is a MAC privilege that applies to root as well. It is attributed to the **responsible code**, not simply the process calling `open()`. Scripts are attributed to their interpreter, and daemonizing can break the attribution ([Quinn, "On File System Permissions", rev. 2026-09-18](https://developer.apple.com/forums/thread/678819)).
- Users report:
  - Granting `bash` Full Disk Access was needed for a launchd script ([forum #7150](https://forum.restic.net/t/can-restic-backup-macos-photos-library-from-launchd/7150)).
  - Pointing the grant at the Homebrew Cellar path for restic did not help (restic 0.9.2/Mojave, [#2051](https://github.com/restic/restic/issues/2051)). The working fix there was a **root-owned, mode-0700 Go runner** holding the grant.
  - Platypus apps needed self-signing after Ventura ([forum #4232/8](https://forum.restic.net/t/utilizing-macos-local-apfs-snapshots-for-restic-backups/4232/8)).
  - Homebrew upgrades changed the path and lost the grant ([Backrest #495](https://github.com/garethgeorge/backrest/discussions/495)).
- Unsigned or ad-hoc-signed code has no stable designated requirement, so grants may not survive upgrades ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)).
- A Tahoe 26.1 regression blocked adding CLI binaries to Full Disk Access; it reportedly works again in 26.3 beta ([Backrest #986](https://github.com/garethgeorge/backrest/issues/986)).

### 5.2 Sleep

- **Restic itself takes no power assertion**; there is no `IOPM` or `caffeinate` code in 0.19.1.
- `caffeinate -i` prevents **idle** sleep on battery and AC. `-s` applies to AC only ([caffeinate.8](https://github.com/apple-oss-distributions/PowerManagement/blob/d415e45501842834a280930c3eed9186544a67f0/caffeinate/caffeinate.8#L18-L45)).
- **Forced sleep** (lid close, the Sleep menu item, low battery, thermal) cannot be prevented, only delayed ([QA1340](https://developer.apple.com/library/archive/qa/qa1340/_index.html)).
- Power Nap is not a runtime for third-party jobs ([Apple guide](https://support.apple.com/en-gb/guide/mac-help/mh40774/26/mac/26)).
- **What restic does after a wake (0.19.1)**:
  - **Locks.** The lock monitor compares wall-clock time, because Go's monotonic timers pause during standby. If the lock is overdue it tries a *safe* stale-lock refresh with the backend frozen, and cancels only if its own lock has been removed ([repository/lock.go L183-243](https://github.com/restic/restic/blob/v0.19.1/internal/repository/lock.go#L183-L243); fixed in **0.16.0** [#4274](https://github.com/restic/restic/issues/4274), [CHANGELOG](https://github.com/restic/restic/blob/v0.19.1/CHANGELOG.md#L2608-L2618)).
  - **Stuck requests.** A watchdog aborts requests with no progress after **5 min** (`--stuck-request-timeout`), and retries run for up to 15 min ([http_transport.go L143-150](https://github.com/restic/restic/blob/v0.19.1/internal/backend/http_transport.go#L143-L150), [global.go L598-619](https://github.com/restic/restic/blob/v0.19.1/internal/global/global.go#L598-L619)).
  
  So a restic 0.19.1 process *can* survive an ordinary sleep. Whether it does in practice on a Mac talking to S3 is **not established** by any well-specified report. A supervisor must still expect restic to exit and plan to restart it.

## 6. Files changing during the backup, and APFS snapshots

- **No change detection while reading (0.19.1).** The archiver stats the opened file and builds the node's metadata from that pre-read stat ([file_saver.go L151](https://github.com/restic/restic/blob/v0.19.1/internal/archiver/file_saver.go#L151)). It sets `Size` from the bytes actually chunked ([L168-185](https://github.com/restic/restic/blob/v0.19.1/internal/archiver/file_saver.go#L168-L185)) and never re-stats afterwards. A file modified during the read is stored silently, possibly torn. It will be re-read on the *next* backup because its mtime or ctime differs ([fileChanged, archiver.go L631-657](https://github.com/restic/restic/blob/v0.19.1/internal/archiver/archiver.go#L631-L657)). Restic reads each file only once, so the hash always matches the stored data ([maintainer, forum #264](https://forum.restic.net/t/what-happens-if-file-changes-during-backup/264)).
  - The "file has changed" warning users quote dates from the **old archiver** ([v0.8.3 archiver.go L146](https://github.com/restic/restic/blob/v0.8.3/internal/archiver/archiver.go#L146)), which was replaced in 0.9.0.
  - Borg 1.4.5, by contrast, flags such files with `C` ([archive.py L1605-1633](https://github.com/borgbackup/borg/blob/1.4.5/src/borg/archive.py#L1605-L1633)).
  - I did not find an open restic issue requesting this feature; GitHub search was rate-limited during this research.
- **APFS snapshots in restic: still open** ([#3714](https://github.com/restic/restic/issues/3714), filed against 0.13.1). `--use-fs-snapshot` is registered only on Windows ([cmd_backup.go L150-152](https://github.com/restic/restic/blob/v0.19.1/cmd/restic/cmd_backup.go#L150-L152)).
- **External recipe.** `tmutil localsnapshot` takes the snapshot. `/sbin/mount_apfs -s <snap> /System/Volumes/Data <mnt>` mounts it; on modern Macs that is the Data volume, not `/`. The recipe needs root and Full Disk Access for the responsible process ([forum #4232](https://forum.restic.net/t/utilizing-macos-local-apfs-snapshots-for-restic-backups/4232), [path fix #4232/13](https://forum.restic.net/t/utilizing-macos-local-apfs-snapshots-for-restic-backups/4232/13), [mount_apfs(8)](https://github.com/keith/xcode-man-pages/blob/46d6bd5d4488143b1928411eb2bbaa262e712e0a/docs/mount_apfs.8.html#L63-L113)). Calling the native `fs_snapshot_*` API from your own binary needs an Apple entitlement on top of root ([fs_snapshot_create.2 L73-87](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/fs_snapshot_create.2#L73-L87)).
  - External volumes that are not in Time Machine can't be snapshotted with `tmutil` ([forum #10488](https://forum.restic.net/t/restic-backup-from-macos-apple-apfs-snapshot-of-external-drive-without-time-machine/10488)).
- **Retention vs weeks.** Time Machine local snapshots normally last about 24 h ([Apple](https://support.apple.com/en-us/102154)). However, **a mounted snapshot cannot be deleted** (EBUSY) ([fs_snapshot_create.2](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/fs_snapshot_create.2#L73-L87)). Keeping one mounted for weeks therefore pins changed blocks, which **costs local disk**. That is in direct tension with the user's nearly full disk.
- **Required flag.** Each snapshot mount has a new device ID, so every directory appears changed. Fix: `RESTIC_FEATURES=device-id-for-hardlinks`, an alpha flag in 0.19.1 ([registry.go L11, L22](https://github.com/restic/restic/blob/v0.19.1/internal/feature/registry.go#L22); [archiver.go L264](https://github.com/restic/restic/blob/v0.19.1/internal/archiver/archiver.go#L264); report: 120,484 directories marked changed → 46, [forum #10494](https://forum.restic.net/t/all-dirs-changed-with-every-backup/10494), restic 0.18.1).
- **Paths.** Restic stores the absolute mount path, and there is no `--set-path` ([#2092](https://github.com/restic/restic/issues/2092) open). The workaround is to `cd` into the mount and back up relative paths. The snapshot metadata still records the absolute source path, so use a stable mountpoint so parent-snapshot matching works ([040_backup.rst L284-321](https://github.com/restic/restic/blob/v0.19.1/doc/040_backup.rst#L284-L321)).
- **iCloud "dataless" files.** Since **0.19.0**, `--exclude-cloud-files` works on macOS 14+ and avoids forcing downloads of cloud-only placeholders during a backup ([CHANGELOG #5352](https://github.com/restic/restic/blob/v0.19.1/CHANGELOG.md#L507-L519); `SF_DATALESS` check in [stat_darwin.go L41-55](https://github.com/restic/restic/blob/v0.19.1/internal/fs/stat_darwin.go#L41-L55)). Without it, a full-disk backup can *pull iCloud content onto a nearly full disk*. This is a plausible, unverified contributor to the user's disk-full failure.

## Implications for the map

**Supervisor daemon**
1. **Make the supervisor the only Full Disk Access holder and the only launchd entry point.** It should be a signed, stably installed native Go binary that execs restic directly; no shell or interpreter in between. Pin and ship the restic binary at a stable path rather than following Homebrew. Re-test the Full Disk Access grant on every upgrade.
2. **Launchd shape.** Either:
   - (a) a **root LaunchDaemon** with the **System keychain**. It works without a login and can mount APFS snapshots, or
   - (b) a **`gui/<uid>` LaunchAgent** with the **login keychain**. It is simpler, but runs only while the user is logged in, and the keychain may lock on sleep.
   
   APFS snapshot mounting needs root, which points toward (a), possibly with a small agent for UI and notifications. **This is a decision for grilling.**
3. **The supervisor owns its own schedule and lifecycle** (`KeepAlive`, plus listening for IOKit sleep and wake). It should not rely on `StartCalendarInterval`.
   - Take an `IOPMAssertion` (PreventUserIdleSystemSleep), optionally only on AC power.
   - On wake, wait for the network and S3 to be reachable before (re)starting restic.
   - Stop restic with SIGTERM, then classify the exit code (0, 1, 3, 11, 12, 130).
   - Never run `unlock --remove-all` automatically.
4. **Secrets.**
   - Repository password: `--password-command` pointing at the supervisor binary itself in a "print secret" mode. That gives a stable ACL identity, unlike `/usr/bin/security`, but needs cgo or a purego loader to call the Security framework (see the pure-Go tension in §4.3).
   - S3 keys: either the same helper as a `credential_process`, configured in a dedicated shared-credentials file, or env vars injected into restic's environment. Use static keys, or refreshing STS via `credential_process` only.
   - Wrap restic's startup in a deadline, because the password command has no timeout.
5. **Consistency policy.** Restic doesn't detect files changing mid-read, and a mounted APFS snapshot pins disk space for as long as it stays mounted. Options:
   - (i) back up live files and rely on the next run to re-read changed ones;
   - (ii) use a **fresh snapshot per run**, which bounds how long blocks are pinned and works because restic dedups across runs;
   - (iii) use one long-lived snapshot.
   
   Option (ii) fits the low-disk goal best. If snapshots are used, set `RESTIC_FEATURES=device-id-for-hardlinks`, `cd` into a stable mountpoint and back up relative paths, and fail closed if the mount fails.
6. Always pass `--exclude-cloud-files` (0.19.0+), so the backup doesn't pull iCloud data onto a nearly full disk.

**Read-only client**
- Restic's backup lock is non-exclusive, so browsing while a backup runs is already allowed (the locking ticket owns the details). The real conflict is wrappers that **auto-unlock** and remove other hosts' locks. The supervisor must not do that, or the client and supervisor must agree on a lock policy.
- If the client is pure Go and uses no locks, it never touches the Keychain on the backup Mac, but it needs its own credential story: read-only S3 keys plus the repo password on the second machine.

**Low-disk / low-RAM**
- Two new sources of local disk use to budget: **APFS snapshot block pinning**, and **iCloud dataless materialization**. Kopia's and Duplicacy's cache reports show other tools need large local caches too.

**New questions / candidate tickets**
- Daemon (root, System keychain, APFS) vs GUI agent (login keychain): grilling.
- Pure Go vs cgo for Keychain access: is a stable ACL identity worth cgo? Evaluate purego/`dlopen` of Security.framework.
- Prototype: a launchd daemon in Go that takes a power assertion, gets wake notifications and runs `tmutil` + `mount_apfs`, measuring how much disk a snapshot pins over a multi-day run.
- Can resumable progress the user can see (Kopia-style checkpoints) be built around restic, e.g. with backups of growing subtrees each creating real snapshots, rather than relying on restic's rescan-on-retry? This links to the interrupted-first-backup ticket.
